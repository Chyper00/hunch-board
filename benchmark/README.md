# Benchmarks: with Hunch, with a plain prompt and with grill-me

The question: does an AI build better from what Hunch hands it than from the alternatives? Each benchmark is the same app, built by agents that do not know about each other.

**Every benchmark has these three arms: current Hunch, grill-me and a plain prompt.** The report compares the three. An extra arm is optional, such as the production release of Hunch (`hunch-prod/`) when the question is whether a new version improved.

- **With Hunch** (`with-hunch/`): receives the Build with AI pack.
- **A paragraph** (`simple/`): receives a paragraph, as a person would write it.
- **Grill-me** (`grill-me/`): receives the same paragraph and the [grill-me](https://github.com/mattpocock/skills) skill. Before building, it interviews "the person": a second agent that only knows the Hunch board.

Results of every benchmark: [`RESULTS.md`](RESULTS.md).

## How to read the report

```bash
npm run bench:report        # prints the table of every benchmark and rewrites RESULTS.md
```

- **`RESULTS.md`:** one table per benchmark, with cost, behavior, tests, code and process (see "What each number means").
- **`<name>/REPORT.md`:** the full report of one benchmark: what each agent received, the results, the decisions read one by one, the defects in Hunch that were found and the limits of the test.
- **`<name>/metrics.json`:** the raw numbers that feed the table.

On GitHub, the `.md` files render. Locally, any Markdown viewer works (in VS Code, `Cmd+Shift+V`).

## What each number means

| Group | Number | How it is measured |
| --- | --- | --- |
| Cost | Tokens, tool calls, time | What each agent's notification reports, written in `runs.json`. For grill-me, it is the interview plus the build; the simulated person's tokens are a separate row. |
| Behavior | Probe: rules from the board | Black-box scenarios taken from the rules, with the app actually running. It applies to every side. |
| | Probe: contract | The exact HTTP status codes only the board defined (409, 422, 403). Counted apart, because the paragraph did not know them. |
| | Robustness | Bad input, the same for any API ([`tools/robustness.mjs`](tools/robustness.mjs)): a body that is not JSON, wrong types, 1 MB, an unknown route, the wrong method, an id that is not a number. It passes with a 4xx and the app still up. |
| | 5xx responses | How many server errors appeared during the whole probe. |
| Tests | Tests passing | The project's test command (`node --test`). |
| | Line, branch and function coverage | Node's own coverage (`--experimental-test-coverage`), of the code only, without the tests. |
| Code | Lines, files, largest file | Without the tests. |
| | Longest function, functions over 40 lines, complexity, nesting, duplication | [`tools/quality.mjs`](tools/quality.mjs), approximate and with no packages. Complexity = 1 + the `if`s, loops, `case`s, `catch`es, `&&`, `\|\|`, `??` and `?:` of each function. Duplication = the share of lines of 30 characters or more that appear more than once. |
| | Files that mix HTTP and SQL | A file that reads the request and also builds SQL. |
| | Syntax errors | `node --check` on each file. |
| | Imports outside the shape | `npm run hunch -- check` with the code board in `design/`. "Does not follow the folders" when the code does not even use the board's folders. |
| Process | Decisions made alone | The lines of `DECISIONS.md`. Read them one by one in `REPORT.md`: the number alone mixes product choices with implementation notes. |
| | Questions asked | On grill-me, how many questions the person answered. |

## Shape of a benchmark

```
benchmark/<name>/
  design/            the board in Hunch: board.hunch and boards/<key>.hunch (no agent sees this)
  with-hunch/        what Build with AI generates + the app the Hunch agent built
  simple/            PROMPT.md with a paragraph + the app the other agent built
  grill-me/          the same PROMPT.md + .claude/skills/grill-me and grilling + GRILL.md, PLAN.md and the app
  eval/probe.mjs     the black-box probe with the board's rules
  eval/result-*.json the probe result on each app
  runs.json          what only the agent can report: tokens, tool calls, time
  metrics.json       generated by tools/measure.mjs
  REPORT.md          the written report
```

## How to run a benchmark

### 1. Choose the app

Something that fits in one agent session (about 300 to 600 lines), but with **business rules that can be tested from the outside**: limits, states, permissions and dates. Without rules, both sides tie and the test says nothing. So both start equal, the stack is only Node 24 (`node:http`, `node:sqlite` and `node:test`), with no packages.

### 2. Draw it in Hunch

In `benchmark/<name>/design/`, in Hunch's project-folder format:

- **`board.hunch`:** the system (people, the app and the database) with the build spec: product, roles, stories with given / when / then, endpoints with body and responses, entities, rules, permissions, example data and the stack.
- **`boards/<key>.hunch`:** the code inside the app box, with a style (`style clean`, `style hexagonal`…), each box with `[layer=… path=…]`.

You can draw it in Hunch itself (Open folder, edit and Export > Project folder) or write the text. Then check:

```bash
node benchmark/tools/check-design.mjs benchmark/<name>/design
```

It lists errors, shape breaks and what the AI would still have to guess. The goal is "Ready: no problems, nothing to guess.", otherwise the test measures the board and not Hunch.

### 3. Generate the two sides

```bash
node benchmark/tools/export.mjs benchmark/<name>/design benchmark/<name>/with-hunch
```

That writes exactly what Build with AI gives a coding assistant: the pack, with the boards inside the boxes, and the one-line `PROMPT.md`.

In `benchmark/<name>/simple/PROMPT.md`, write a paragraph as a person would: the same idea, the main rules and the same stack, with no structure.

For grill-me, copy the same `PROMPT.md` into `grill-me/` and download the skill (both files, `grill-me` and `grilling`) into `grill-me/.claude/skills/`.

### 4. Run the agents

The agents that build are the same model, run in parallel and receive the text of [`tools/agent-prompt.md`](tools/agent-prompt.md). The text is the same for all of them; only the folder and the port change. Each one works only in its folder, may not ask and records what it chose alone in `DECISIONS.md`.

Grill-me has two phases:

1. **Interview.** The agent receives [`tools/grill-prompt.md`](tools/grill-prompt.md) and returns a round of questions. The person is another agent, with [`tools/person-prompt.md`](tools/person-prompt.md): it only reads `design/` and answers "yes" to the recommendation when the board says nothing. You carry each round from one to the other (`SendMessage`), until the agent writes `PLAN.md` and says "READY TO BUILD".
2. **Build.** The same agent receives the rules in `agent-prompt.md` (no more questions) and builds.

When they finish, write in `benchmark/<name>/runs.json` what each agent's notification reports:

```json
{
  "idea": "one sentence about the app",
  "date": "YYYY-MM-DD",
  "hunchCommit": "the Hunch commit that generated the pack",
  "with-hunch": { "tokens": 0, "toolUses": 0, "seconds": 0 },
  "simple": { "tokens": 0, "toolUses": 0, "seconds": 0 },
  "grill-me": { "tokens": 0, "toolUses": 0, "seconds": 0, "personTokens": 0, "questions": 0 }
}
```

### 5. The probe

In `benchmark/<name>/eval/probe.mjs`, a black-box probe. Use [`shelf/eval/probe.mjs`](shelf/eval/probe.mjs) as the model:

- **It starts the app** as a process, with its own `PORT` and `DB_PATH`. Use [`clinic/eval/probe.mjs`](clinic/eval/probe.mjs) as the model for three sides.
- **It runs scenarios taken from the board's rules.** Each scenario is a `check(name, passed, detail)`.
- **A small adapter per app** translates the routes and how to say who is calling. Everything else is the same for both.
- **Behavior and the contract stay separate.** "A fourth loan is refused" applies to everyone; "with status 422" only the board defined, so it is a separate check (`check(name, passed, detail, true)`).
- **At the end, it calls `robustness()`** from [`tools/robustness.mjs`](tools/robustness.mjs) and writes the result in the same JSON, with the total of 5xx responses.

```bash
node benchmark/<name>/eval/probe.mjs benchmark/<name>/with-hunch with-hunch 4201 > benchmark/<name>/eval/result-with-hunch.json
node benchmark/<name>/eval/probe.mjs benchmark/<name>/simple simple 4202 > benchmark/<name>/eval/result-simple.json
node benchmark/<name>/eval/probe.mjs benchmark/<name>/grill-me grill-me 4203 > benchmark/<name>/eval/result-grill-me.json
```

### 6. Measure and write

```bash
node benchmark/tools/measure.mjs benchmark/<name>   # tests, coverage, quality, probe, shape -> metrics.json (run from the repository root)
npm run bench:report                                # updates RESULTS.md
```

Then `REPORT.md`:

- **the result,** in a table;
- **the decisions on each side, one by one:** which were product, which were implementation, and which came from defects in the Hunch pack;
- **whether Hunch was better,** and at what cost;
- **the defects in Hunch the test revealed,** which should be fixed and recorded;
- **the limits of the test:** one run, who wrote the board, who scored it.

## Rules that keep the test honest

- **The same model, the same instruction text and the same stack** on every side.
- **Grill-me's person knows what the board knows, and nothing more.** That compares the path of the knowledge to the AI, not who knows more.
- **The board should leave zero questions.** Otherwise the test measures a bad board.
- **No agent that builds sees another agent's folder or `design/`.** Only the simulated person reads `design/`.
- **Score with the probe, not with an impression.** What only the board defined (status codes, routes) is counted apart from behavior.
- **Write down the Hunch commit.** The pack changes with every fix, and a result only holds for the version that generated it.
